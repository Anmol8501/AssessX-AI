# Windows Secure Kiosk — OS-level lockdown (Phase 4B.5, Mode B)

**Status:** foundation implemented 2026-09-25 (compatibility detection + administrator provisioning
artifact). Applying kiosk mode is an **administrator** action on a dedicated exam machine; the
AssessX application never does it.

> **Configuration generated but deployment not yet manually verified.** The provisioning artifacts
> below are generated by AssessX and correct in structure, but have **not** been applied and tested
> on a disposable Windows Pro/Enterprise/Education machine. Treat them as a reviewed template to
> validate before production use — not as a confirmed working deployment.

## Why this exists

A normal Windows desktop application — including AssessX — **cannot** reliably stop Windows
shortcuts such as Alt+Tab, the Windows key, Win+Tab or the Start menu. This was verified on real
hardware: from those, a candidate can give keyboard focus to another application (Notepad, a
browser) running behind the exam window and type into it. AssessX's Standard mode **detects and
records** this (`FOCUS_LOST`) and covers the exam until the candidate returns, but it cannot prevent
it.

Preventing it requires **Windows itself** to restrict the account. AssessX is a **classic Win32
desktop application**, so the supported mechanism is **multi-app Assigned Access** — the desktop app
is an `<App DesktopAppPath="…">` in `<AllowedApps>`, with the taskbar hidden and the Start layout
emptied, so AssessX is the only launchable application. (The single-app `<KioskModeApp>` element is
for UWP/Store apps only and does **not** accept a desktop path.) The configuration is applied through
Microsoft's **MDM Bridge WMI provider** (`root\cimv2\mdm\dmmap` → `MDM_AssignedAccess`). A stricter
alternative for a true single-app shell is **Shell Launcher v2** (Enterprise/Education/IoT), which
this generator does not yet produce.

```
Windows (Assigned Access kiosk account)
        └── AssessX is the only application the account can run
              └── AssessX application-level controls (Phase 4B) still apply on top
```

The two layers complement each other: kiosk stops OS-level app switching; AssessX still enforces
fullscreen, clipboard, context-menu, print and screen-capture controls and records proctoring
events.

## Two modes

| | Standard (Mode A) | Secure Kiosk (Mode B) |
|---|---|---|
| What restricts the machine | AssessX only | Windows (Assigned Access) + AssessX |
| Alt+Tab / Windows key / Start menu | **detected, not blocked** | **blocked by Windows** |
| Launch another app | possible; not detected unless it has a window at readiness | prevented by Windows |
| Who sets it up | nobody (works on any PC) | an administrator, in advance |
| Suitable for | personal devices | institution-managed exam machines |

AssessX shows which mode it is in (admin **Settings → Secure Kiosk Mode**), read from the OS, not
from a client flag. The status card never uses words like "unbreakable" or "100% cheat-proof".

## What AssessX provides (and does not)

In **Settings → Secure Kiosk Mode** (installed app, admin):

- **Compatibility check (read-only).** Reads the Windows edition and whether Assigned Access is
  supported (Pro, Enterprise, Education, IoT — not Home), and whether this session is already a
  kiosk. It writes nothing.
- **Prepare kiosk configuration.** Generates three text artifacts for an administrator to review
  and run **elsewhere**: an Assigned Access XML profile, an apply script, and a remove/recovery
  script. AssessX does not run them.

AssessX **never**:

- enables kiosk mode, silently or otherwise;
- modifies the registry, policies, or the current account;
- converts the developer's or candidate's PC into a kiosk;
- reboots into kiosk mode.

Applying a kiosk requires administrator rights and a person explicitly running the apply script.

## Prerequisites

- Windows 10/11 **Pro, Enterprise, Education, or IoT Enterprise** (Assigned Access is not on Home).
- Administrator access to the exam machine.
- AssessX installed (default `C:\Program Files\AssessX\assessx-desktop.exe`).
- A **dedicated exam machine**, not a personal device.

## Deployment (administrator)

1. On the exam machine, open AssessX as an admin → **Settings → Secure Kiosk Mode**.
2. If the edition is unsupported, the card says so — stop; kiosk is not available.
3. Set the kiosk account name (default `assessx-exam`) and **Prepare kiosk configuration**.
4. Review the generated **Assigned Access XML** and **apply script**. The apply script:
   - requires an elevated PowerShell (`#Requires -RunAsAdministrator`);
   - prompts for a typed `YES` before doing anything;
   - creates the local kiosk account if missing;
   - checks AssessX is installed at the expected path (edit the path if your install differs);
   - applies the multi-app Assigned Access XML via the MDM Bridge WMI provider
     (`Get-CimInstance … MDM_AssignedAccess` → set `Configuration` → `Set-CimInstance`).
5. **Validate on a disposable machine first.** Then sign in as the kiosk account to start a secure
   exam session.

The XML's `<App DesktopAppPath>` already points at the executable path you provided (or the default
install path); no manual XML edit is needed unless the install location differs.

## Validation

- Sign in as the kiosk account: only AssessX should run; there is no Start menu, taskbar or app
  switching.
- Alt+Tab, the Windows key and Win+Tab should not switch to another application.
- AssessX's own controls (fullscreen, clipboard, etc.) should still work.
- The admin **Secure Kiosk Mode** card should read **Secure Kiosk** for that session.

## Recovery and removal

- **Recovery:** sign in as a *different* administrator account and run the generated **remove
  script** (it clears `MDM_AssignedAccess.Configuration`), or use **Settings → Accounts → Other
  users**, or **Settings → Accounts → Set up a kiosk** to remove the configuration. The kiosk account itself is left in place; delete it with `Remove-LocalUser` if no longer
  needed.
- Keep an administrator account that is **not** the kiosk account, so you can always sign in to
  remove the configuration.

## Limitations and honesty

- **Not deployment-verified.** The generated multi-app Assigned Access XML and the MDM-Bridge apply
  script are structurally correct and use Microsoft-supported mechanisms, but have not been applied
  and tested on a real supported machine here. The exact XML escaping and WMI behaviour can vary by
  Windows build and must be validated on a disposable Pro/Enterprise/Education machine before use.
- For a *true* single-application shell (no taskbar at all), **Shell Launcher v2** is the stronger
  mechanism; it needs Enterprise/Education/IoT and is not generated here.
- AssessX detects "kiosk active" by the absence of the normal Explorer shell for the session; this
  is a signal, not a cryptographic guarantee.
- This does not defend against hardware attacks, a second device, or someone photographing the
  screen — those are outside OS lockdown.
- **Do not** apply kiosk mode on the development machine or any personal PC. Use a disposable
  machine or VM to test deployment.
